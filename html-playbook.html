Repo HTML Playbook

A practical guide for when this repo should use HTML artifacts instead of plain markdown.

Essence Decision Rule Artifact Types Canvas Pattern Lifecycle Repo Rules Artifact Chooser Prompts
HTML is not prettier markdown. It is an operating surface.

Use HTML when the reader needs to see, compare, interact, or decide.

Markdown stays excellent for canonical instructions and small specs. HTML earns its keep when a dense artifact must be read, navigated, reviewed, shared, or used as a temporary decision interface.

Density Tables, diagrams, callouts, and spatial layouts beat long prose for complex repo context.
Clarity Navigation, visual grouping, and color make large agent outputs easier to actually read.
Review Diffs, risk maps, test matrices, and annotations help fresh reviewers inspect the right thing.
Feedback Buttons, tabs, filters, and copy prompts turn a static report into a lightweight workbench.
01 / essence

The reference article's core lesson for this repo.

Agents are now good enough to produce documents that exceed what markdown can comfortably express. The value is not visual decoration. The value is keeping the human in the loop when the artifact becomes too large or multidimensional for a flat text file.

Repo translation: use HTML to make complex agent work inspectable. Then distill durable decisions back into the canonical files: `STRATEGY.md`, `CONTEXT.md`, `AGENTS.md`, ADRs, issues, tests, and code.

Not decoration

HTML should reveal structure

Use it to show pipelines, alternatives, ownership maps, test matrices, and consequences that prose would bury.

Not permanent truth

HTML is usually a reader surface

Durable truth still belongs in maintainable source files. HTML can explain and coordinate, but it should not become a hidden policy store.

Not only reports

HTML can be a temporary tool

For triage, prioritization, prompt tuning, UI comparison, or BpSpec inspection, a single HTML file can become a purpose-built editor.

02 / rule

Choose HTML when one of four pressures appears.

Do not make every document an HTML document. Make HTML when the job has visual, comparative, interactive, or review pressure.

03 / types

Repo-specific HTML artifact types.

These are the places HTML can materially improve Unifier Toolkit work without creating documentation rot.

Type Use when Suggested path Canonical truth after use
Operating explainer Explaining agent workflow, repo strategy, or system shape. docs/*-strategy.html, docs/*-playbook.html AGENTS.md, STRATEGY.md, CONTEXT.md
Implementation plan companion A CE plan needs diagrams, risk maps, flowcharts, or UI mockups. docs/plans/<slug>.html docs/plans/<slug>.md, GitHub issues
Architecture map Understanding a module requires bouncing across many files or concepts. docs/architecture-*.html ADRs, CONTEXT.md, module interfaces, tests
Code review explainer A branch changes important behavior and a plain diff is not enough. docs/reviews/<branch>.html if retained PR review, commits, tests, follow-up issues
Prototype or comparison board Choosing between UI flows, layouts, copy, or interaction models. docs/prototypes/<topic>.html Accepted design, issues, implementation files
Throwaway editor Manual text prompts are a bad interface for a structured decision. docs/tmp/<topic>-editor.html Exported JSON, issue body, code config, or plan update
Research report Summarizing source docs, git history, test results, or Sandcastle output. docs/reports/<topic>.html ADRs, issues, solution docs, strategy updates
04 / canvas

Every useful HTML artifact should have a job.

A good HTML artifact is not "a markdown doc rendered in a browser." It is a purpose-built canvas with navigation, visual structure, and an export or next-action path.

Orient

First viewport

State what the artifact helps decide or understand. Do not hide the point below decorative sections.

Navigate

Stable sections

Use a sidebar or top nav so large artifacts are scannable. Section IDs should be meaningful.

Visualize

Maps and matrices

Use SVG, tables, grids, risk maps, timelines, and tabs where prose would create cognitive load.

Return

Copy or export

Include copy prompts, JSON export, or a clear "distill into source of truth" checklist.

Quality test: if the reader cannot answer "what should I do next?" after reading the artifact once, the HTML is pretty but not useful.

05 / lifecycle

HTML artifacts should feed the repo, not become a side universe.

The playbook is to use HTML for comprehension and decision pressure, then push durable outcomes back into maintainable artifacts.

1

Create

Name the decision or comprehension problem. Read the relevant source files. Build only the interface needed for that problem.

2

Inspect

Use the HTML to compare alternatives, trace flows, review code, or export structured edits.

3

Decide

Record which interpretation, design, issue ordering, or architecture shape is accepted.

4

Distill

Move durable truth into AGENTS.md, STRATEGY.md, CONTEXT.md, ADRs, CE plans, issues, tests, or code.

5

Retire or keep

Keep HTML that remains useful as a reader surface. Retire throwaway editors and stale reports once their output has been absorbed.

06 / rules

Repo rules for HTML files.

These constraints keep HTML useful without making the repository hard to review or maintain.

Do
  • Use self-contained HTML, CSS, and small vanilla JS unless the artifact must run inside the app.
  • Link back to canonical markdown files and code paths that informed the artifact.
  • Use visual structure that reduces reading effort: grids, tables, SVG, tabs, filters, and timelines.
  • Include a clear next-action or export path when the artifact is interactive.
  • Run basic HTML sanity checks for anchors and copy targets before handing off.
Avoid
  • Do not put hidden product rules only in HTML.
  • Do not use HTML for tiny edits, short notes, or simple issue bodies.
  • Do not create a large artifact without naming what decision it supports.
  • Do not preserve throwaway editors after their export has been applied.
  • Do not let HTML reports replace tests, import checks, issue state, or human QA.
07 / chooser

Pick the artifact shape before asking an agent to build it.

Use this interactive chooser as the mental model. Select the pressure you feel, then copy the output into the next prompt if useful.

Comparison board

Use when the human needs to choose between approaches, UI flows, architecture options, or issue ordering.

  • Show each option in a uniform grid.
  • Name the trade-off each option makes.
  • Include a recommendation and why.
  • End with a copyable decision summary.
08 / prompts

Prompts to create good HTML artifacts.

These prompts preserve the essence: HTML should make the work easier to inspect and the next action easier to take.

General repo artifact

Create a self-contained HTML artifact for this repo. Use it only where HTML adds clarity beyond markdown: visual hierarchy, diagrams, comparison, interaction, or review. Link to the canonical files that carry durable truth. Include navigation, at least one useful visual structure, and a clear next-action or copyable handoff.

Code review explainer

Create an HTML code review explainer for this branch. Read the diff, linked issue, linked CE plan, tests, and relevant modules. Show the behavior change, risk map, affected interfaces, test coverage, and any review findings. Do not replace the actual review; make it easier for a fresh reviewer to inspect the change.

Plan companion

Create an HTML companion to the CE implementation plan. Render the issue graph, module map, test matrix, and open risks. Keep the markdown plan canonical for implementation units; use HTML to make dependencies and trade-offs visible.

Throwaway editor

Create a single-file HTML editor for this structured decision. It should let me reorder, tag, filter, or edit the data visually, warn about obvious inconsistencies, and provide a copy button that exports the final result as markdown or JSON for Codex.
This HTML playbook is a reader surface. The durable repo contract lives in AGENTS.md, product direction in STRATEGY.md, domain vocabulary in CONTEXT.md, and implementation work in CE plans, GitHub issues, tests, and code.
